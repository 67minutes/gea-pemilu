# Production capacity rehearsal

Voting is in person on three kiosk laptops, so election-day load is small; this rehearsal is optional
and checks headroom and correctness under concurrency. **It has not been certified.** Run against a separate synthetic database and
the exact app/database sizes, region, pooler, worker counts, password hasher, proxy, and
TLS settings intended for election day. A local Django development server is not a capacity result.

Install [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/). The harness uses 500 distinct voters,
ramping over 60 seconds, sustaining 500 active sessions for 15 minutes, then ramping down.
Each voter logs in, chooses every office, reviews, finalizes (which logs them out), logs in again,
retries finalizing with different candidates (which must change nothing), and continues browsing the dashboard. A second mode attempts 500 logins simultaneously.
`MODE=smoke` runs two users for two iterations to validate the harness itself; it does not certify capacity.

1. On the **isolated rehearsal environment**, use an empty PostgreSQL database and `DEBUG=true`
   only while creating the fixtures. Do not change the production database or weaken the password hasher.

   ```powershell
   uv run python manage.py migrate
   uv run python manage.py seed_demo --voters 500 --open --output loadtest/voters.json
   ```

2. For a remote rehearsal, transfer the private synthetic credential file to the load generator.
   Serve with the production image and configuration, including `DEBUG=false`, except
   `KIOSK_REQUIRED=false`: k6 is not an enrolled laptop. Set this **only on the isolated rehearsal host**,
   never on the election service. Configure real
   deployment secrets (no live emails are generated by `seed_demo`). Keep the database isolated.

3. From the repository root, run:

   ```powershell
   k6 run -e BASE_URL=https://your-rehearsal-host -e ALLOW_SYNTHETIC_ELECTION=yes --log-format raw --console-output output/load-ballots.jsonl loadtest/voting.js
   k6 run -e BASE_URL=https://your-rehearsal-host -e ALLOW_SYNTHETIC_ELECTION=yes -e MODE=burst --log-format raw loadtest/voting.js
   ```

   `VOTERS_FILE` is relative to the JavaScript file. The default is `loadtest/voters.json`.
   Run the burst test after the steady test (existing votes do not affect login).

4. On a trusted operator machine with the isolated database URL and `DEBUG=true`, reconcile ballots:

   ```powershell
   uv run python manage.py verify_rehearsal output/load-ballots.jsonl --expected-voters 500
   ```

5. Archive both summary JSON files, the ballot reconciliation output, deployment configuration,
   and Render CPU/RAM/database-pool metrics. Fill in `docs/VALIDATION.md`. Delete synthetic credentials
   after verification. Start with a clean database for a new steady test.

Pass gates: vote p95 <2s; login burst p95 <10s; unexpected errors <0.5%; all checks pass;
all 500 acknowledged ballots (1,000 votes) match the database exactly. k6 exits nonzero on threshold failure.
Review the summary's `login_duration` for both modes. If password verification saturates CPU,
increase web CPU/instances, preserving hashing strength, and rerun. If lock/pool waits grow,
inspect database resources and queries before increasing connection counts.

One 2-worker × 2-thread instance holds at most 4 web connections, plus cron and migrations.
Leave headroom within PostgreSQL's limit and monitor the managed pool. Browser concurrency does
not equal database connection count.
